# Client Decisions and Provisional Assumptions

Status legend: **CONFIRMED BASELINE** (from supplied documents or explicit user
instruction), **RECOMMENDATION** (our technical proposal), **INFERENCE** (safe
assumption needed to proceed), **CLIENT CONFIRMATION REQUIRED** (must be answered
before the related module is treated as final).

Nothing here is a hidden policy decision. Where the documents were silent, the
build used a reversible default and recorded it below.

| ID | Category | Decision / assumption | Why it was needed | Impact if wrong | Status |
| --- | --- | --- | --- | --- | --- |
| D-001 | RECOMMENDATION | Use **React + Fastify + PostgreSQL** with an own API instead of Supabase browser clients. | Environment has no Docker/Supabase; master prompt allows a server-side API. Keeps DB credentials off the browser. | If the client mandates Supabase, the API layer would be ported; schema and UI survive. | Provisional for this build |
| D-002 | INFERENCE | Seed timezone is `Asia/Kolkata`; instants render in the **school timezone**, date-only values are stored as `DATE`. | Blueprint context is Indian schools and the demo needs a concrete calendar. | Timestamps/calendar boundaries shift for other regions. | CLIENT CONFIRMATION REQUIRED |
| D-003 | INFERENCE | Academic year runs **1 April – 31 March**; demo year is `2026-27`. | Needed for seed data and sections. | Real calendar differs. | CLIENT CONFIRMATION REQUIRED |
| D-004 | RECOMMENDATION | **RLS policies now exist** for tenant-scoped tables (migration `0018_rls.sql`) with an optional restricted `erp_app` role. The running API still connects as the database owner, so policies are tested but not enforced in normal operation; guards and scoped SQL remain the primary control. | Provides a tested path to database-level isolation without breaking the local owner-based setup. | Until the API runs as `erp_app` with per-request `app.school_id`, tenant isolation still depends on application code. | Provisional; enforce before pilot |
| D-005 | INFERENCE | Admission numbers use `ADM-<year>-<5-digit sequence>` with one counter per school, **not reset per academic year**. | The starter schema exposes `school_counters`; admissions must be unique. | If the school resets numbering each year, historical uniqueness logic changes. | CLIENT CONFIRMATION REQUIRED |
| D-006 | RECOMMENDATION | Exactly **one active academic year** per school; activating a year closes the previous one transactionally. | Prevents ambiguous enrollment scope. | Schools running parallel curricula/years need a different model. | CLIENT CONFIRMATION REQUIRED |
| D-007 | INFERENCE | Classes are school-wide (`G1`–`G5` demo); sections belong to one academic year with capacity 40. | Simplest model matching the starter schema. | Multi-campus/section naming rules may differ. | CLIENT CONFIRMATION REQUIRED |
| D-008 | INFERENCE | Guardians need `portal_access_status = verified` to see a child; at most **one current primary guardian** per student. | Enforces the "verified linked children" rule and avoids ambiguous primary contact. | If two parents may both be primary, the partial unique index must be relaxed. | CLIENT CONFIRMATION REQUIRED |
| D-009 | INFERENCE | Provisional role matrix: main admin holds every permission, including salary, payroll, leave configuration and safeguarding; finance is fee/report-biased and does not get salary or safeguarding; auditor is read-only; coordinator approves attendance and leave but sees no salary. | Least privilege from the master prompt while keeping the demo usable by one administrator. | Real school staffing will almost certainly split these duties; the concentration of payroll/safeguarding in `main_admin` is a risk. | CLIENT CONFIRMATION REQUIRED |
| D-010 | INFERENCE | Student statuses `active/inactive/graduated/transferred/withdrawn`; enrollment statuses `active/completed/withdrawn/transferred`. | Needed for validation and the students list filter. | Existing school vocabulary may differ. | CLIENT CONFIRMATION REQUIRED |
| D-011 | INFERENCE | Password policy: minimum 12 characters for new passwords; login rate limit 10/min; lockout after 10 failures for 15 minutes; session 7 days. | Security hardening without a client policy document. | Too strict/lenient for the school's IT policy. | CLIENT CONFIRMATION REQUIRED |
| D-012 | INFERENCE | Student `date_of_birth` is required; admission requires at least one guardian with relationship and primary flag. | Matches baseline admissions data needs. | Some admissions may arrive without guardians or DOB. | CLIENT CONFIRMATION REQUIRED |
| D-013 | CONFIRMED BASELINE | All bundled demo records are **synthetic**; `db:reset` destroys local data and is blocked on non-local/production URLs. | Master prompt requires synthetic fixtures only. | None if respected; never point it at real data. | Confirmed |
| D-014 | INFERENCE | Fee and exam **policy is configurable and provisional**, not client-confirmed. Fee heads, per-class/year structures, concessions, due dates and refunds are data, not hard-coded rules; grading uses a seeded 8-point scale that can be replaced. Attendance follows the provisional policy recorded in D-017/D-018. See D-019–D-036 for specifics. | The client has not supplied fee/grading policy; the build needed reversible defaults. | Real fee heads, due-date rules, late fees and grading scales may differ. | CLIENT CONFIRMATION REQUIRED |
| D-015 | RECOMMENDATION | No paid services. Production hosting/database/backup provider is **undecided**; current setup is local-only. | Master prompt's free-first rule. | Deployment design still open. | CLIENT CONFIRMATION REQUIRED |
| D-016 | INFERENCE | Parent portal is **read-only** across attendance, fees/receipts, report cards and notices. Contact-the-office copy is shown instead of edit/pay controls. | No approved guardian self-service or online-payment workflow yet. | Parents may expect corrections, requests or payments online. | CLIENT CONFIRMATION REQUIRED |
| D-017 | INFERENCE | Attendance is **one daily register per section/date** with statuses `present`, `absent`, `late`, `half_day`, `excused`. A date must be inside the section's academic year and not later than today in the school timezone. No period-wise model, holiday calendar or attendance threshold is assumed. | Needed to build entry without inventing rules. | Schools using period-wise attendance, different status labels, holidays or minimum-attendance rules need schema/config changes. | CLIENT CONFIRMATION REQUIRED |
| D-018 | RECOMMENDATION | A saved attendance row is **immutable through the register**. Changing it requires a reasoned correction request; a different user holding `attendance.correction.approve` (admin or coordinator) approves or rejects it. One pending request per row; the requester cannot approve their own request. | Prevents silent edits and keeps an auditable approval trail. | If teachers may edit same-day registers freely, or the school wants multi-step approval, the workflow must change. | CLIENT CONFIRMATION REQUIRED |
| D-019 | INFERENCE | **Timetable conflicts** are rejected by the database for the same academic year, day-of-week and period across **section, teacher and room**. Periods are per academic year; rooms are school-wide with a capacity and status. Break periods do not accept slots. | Needed to build a conflict-free grid without a substitution policy. | Substitutions, double periods, shared rooms or part-time teachers may need different constraints. | CLIENT CONFIRMATION REQUIRED |
| D-020 | RECOMMENDATION | **Fee generation** creates one charge per student/year/fee head from the class structure, enforced by a unique constraint (safe to re-run). Concessions are entered per charge with a reason. Payments must allocate their full amount across that student's open charges, capped at each charge balance; overpayment and cross-student allocation are rejected. | Prevent duplicate charges and invented instalment/credit rules. | Instalment plans, advance credit or partial allocation rules may differ. | CLIENT CONFIRMATION REQUIRED |
| D-021 | RECOMMENDATION | **Refunds are payment-level**, capped by the receipt amount, and require review by a different user holding `fees.refund.approve`; self-approval is blocked. An approved refund reduces net collected and raises outstanding, while the charge's own paid amount stays allocation-based. | Separation of duties without inventing a charge-reversal workflow. | If refunds must reverse specific allocations, the ledger model needs a reversal entity. | CLIENT CONFIRMATION REQUIRED |
| D-022 | RECOMMENDATION | **Examination publication** requires at least one recorded mark for every exam subject; publishing locks marks and exposes report cards to guardians; unpublishing reopens entry. Report cards show per-subject marks, grades, totals, percentage and an overall grade, or `incomplete`. The seeded 8-point scale is provisional. | Needed to make results safe to publish without confirmed term/promotion rules. | Term aggregation, weightings, grace marks, promotion/retention and transcript formats are undefined. | CLIENT CONFIRMATION REQUIRED |
| D-023 | INFERENCE | **Leave** is separate from staff status. Non-approvers may request only for their own staff record; overlapping pending/approved requests are rejected; nobody may approve their own request; cancellation is allowed only while pending (approvers may cancel others' pending requests). Leave types, quotas and holidays are now configurable (D-029), but no accrual or carry-forward is assumed. | Needed to implement leave without a confirmed HR policy. | Leave accrual, carry-forward, holiday effects on duration and payroll impact are undefined. | CLIENT CONFIRMATION REQUIRED |
| D-024 | INFERENCE | **Notice visibility** is derived from the actor's server-side roles, never client input: managers see drafts/archives; readers see published, unexpired notices addressed to `all` or their audience (`staff` / `parents` / `students`). Published notices must be archived before deletion. Attachments are capped at 1 MiB decoded and downloads re-check audience visibility. Read receipts are per user. | Prevent audience leakage and destructive edits, and make in-app delivery auditable. | Consent, external delivery channels, retention and attachment malware scanning are undefined. | CLIENT CONFIRMATION REQUIRED |
| D-025 | INFERENCE | **Report attendance rate** is `(present + late + 0.5 × half_day) ÷ marked`; `excused` counts as marked but not attended. Fee report outstanding is `charged − collected` (the fee overview additionally nets concessions and refunds). CSV exports use a UTF-8 BOM. | Needed to display a consistent, explainable figure. | The school may weight late/half days or treat excused days differently. | CLIENT CONFIRMATION REQUIRED |
| D-026 | RECOMMENDATION | Reference reads (academic years, classes, sections, subjects) are allowed with **either** `academic.structure.view` **or** `school.view`, so finance/report users can populate pickers without gaining academic navigation. Writes still require the specific manage permission. | Otherwise fee/report screens break for non-academic roles. | If `school.view` is granted too broadly, read access to structure widens accordingly. | Provisional; revisit with the role matrix |
| D-027 | RECOMMENDATION | Salary is readable only with `hr.employee.salary.view_sensitive`, currently granted to `main_admin` only. Salary audit entries record effective date and currency but **never the amount**. | Least privilege for sensitive pay data. | Schools that split HR/finance duties may need a separate payroll role. | CLIENT CONFIRMATION REQUIRED |
| D-028 | RECOMMENDATION | **Safeguarding** uses `safeguarding.case.view` and `safeguarding.case.manage`, both currently granted only to `main_admin`. Case summaries, note text and student names are excluded from audit payloads. | The workflow needed an access rule; the master prompt gives no named safeguarding role. | Concentrating access in one account is operationally fragile and may not satisfy child-protection policy; a designated safeguarding lead role is likely required. | CLIENT CONFIRMATION REQUIRED |
| D-029 | INFERENCE | **Leave configuration**: leave types carry an annual quota and paid flag; holidays are recorded per calendar year. Balances are derived as quota minus approved/pending days for the selected calendar year, with **no carry-forward** and no backfill before the selected year. Using a holiday does not automatically shorten a request. | Needed to show balances without inventing accrual rules. | Accrual, proration, carry-forward, encashment and holiday-aware duration are undefined. | CLIENT CONFIRMATION REQUIRED |
| D-030 | INFERENCE | **Payroll** runs are monthly per school with draft/approved/paid states; approval requires a different user; amounts are excluded from audit records. No statutory tax, provident-fund, insurance or gratuity rules are built in — deductions are entered explicitly. | Needed to implement a payroll workflow without statutory policy or tax tables. | Real payroll must apply jurisdiction-specific statutory rules and produce compliant payslips; this build cannot be used to pay staff as-is. | CLIENT CONFIRMATION REQUIRED |
| D-031 | RECOMMENDATION | **Late fees** post to a dedicated `LATE-FEE` fee head as an increment to that yearly charge, with one assessment per charge per day. **Instalments** store due dates/amounts and derive status from charge-level allocations rather than storing a separate paid flag. | Needed to implement the features without a confirmed late-fee or instalment policy. | Grace periods, compounding, waivers and instalment-specific payment matching may differ. | CLIENT CONFIRMATION REQUIRED |
| D-032 | INFERENCE | A **transcript** lists every published exam in one academic year and shows per-exam and overall totals. The cumulative grade is intentionally `null` because grading bands may change between exams. | Avoids publishing a potentially misleading cross-exam grade. | Schools may require a cumulative grade, GPA or weighted term result. | CLIENT CONFIRMATION REQUIRED |
| D-033 | INFERENCE | **Student CSV import** is capped at 500 rows; required columns are `first_name`, `class_name`, `section_name`; optional columns are `admission_number`, `middle_name`, `last_name`, `date_of_birth`. Each row is admitted in its own transaction and an import-summary audit event is written. | Needed to implement bulk admission without a client import specification. | Column names, duplicate-handling, guardian columns and row limits may differ. | CLIENT CONFIRMATION REQUIRED |
| D-034 | RECOMMENDATION | **Idempotency** is opt-in via an `Idempotency-Key` header on payment, admission and payroll-run creation, scoped per school/user/route. An identical replay returns the stored response; a mismatched payload is rejected; an in-progress replay is rejected. | Prevents duplicate money/admission/payroll records on retry. | Clients that omit the header get no protection; retention/cleanup policy for keys is undefined. | Provisional |
| D-035 | RECOMMENDATION | **Backup/restore** uses a JSON snapshot of data tables (`to_jsonb` / `jsonb_populate_record`), not `pg_dump`. Restore is local-only, requires `--yes`, and truncates data tables first. | Provides a portable backup path without external binaries. | Not suitable for large production datasets, point-in-time recovery or zero-downtime restore; schema objects are not included. | Provisional |
| D-036 | INFERENCE | **Accessibility scope**: static `eslint-plugin-jsx-a11y` rules are enforced for the web app. No automated browser-based axe/visual test is included. | Accessibility was requested; the free toolchain here supports static linting without adding a browser test dependency. | Static rules do not catch focus order, contrast, zoom or screen-reader issues. | Provisional |

## Open questions that block treating modules as final

1. Fee heads, concessions, due dates, late fees, instalment plans, payment
   providers and receipt numbering (implemented provisionally per D-014,
   D-020, D-021, D-031).
2. Attendance: the provisional workflow is D-017/D-018. Still unconfirmed: holiday
   calendar, cut-off/time-of-day handling, period-wise vs daily register,
   attendance thresholds and the reporting period used on report cards.
3. Examination terms, grading scales, mark entry permissions, report-card
   publication, multi-term aggregation, promotion/retention and transcript format
   (implemented provisionally per D-022, D-032).
4. Timetable periods, teacher allocation rules, substitutions and room sharing
   (implemented provisionally per D-019).
5. Staff/HR scope: leave accrual/carry-forward, payroll statutory rules and
   separation workflows (leave config/balances and payroll implemented
   provisionally per D-029, D-030).
6. Communication channels (email/SMS/WhatsApp), consent, delivery and retention
   (in-app notices, attachments and read receipts implemented per D-024; external
   delivery is not implemented).
7. Safeguarding roles, escalation/referral process, retention and guardian
   communication (case recording implemented provisionally per D-028).
8. Data retention, export and deletion obligations for student/guardian records,
   including retention of CSV export audit metadata.
9. Production hosting, database provider, RLS runtime enforcement, backup
   frequency and recovery targets (backup tooling is provisional per D-035).
